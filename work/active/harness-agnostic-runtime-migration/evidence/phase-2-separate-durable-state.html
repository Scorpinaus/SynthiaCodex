Recovery and compatibility

Import and commit protocol

Step 1

Detect

A valid manifest selects split storage. Without one, the adapter looks for the release 0.1.0 source or an earlier import backup.

Step 2

Preserve

The old settings document is copied byte for byte once. Invalid backups fail closed instead of silently importing defaults.

Step 3

Migrate sequentially

The registry requires exactly n to n+1. Missing, skipping, and downgrade paths throw explicit errors.

Step 4

Commit last

Data documents are written before the manifest. A loader accepts only the manifest generation and restores matching backups if a later generation was interrupted.

Honest migration log

Mistakes and corrections

The first contracts build missed a harness namespace

DurableStateContracts.cs used KnownHarnessIds without importing its namespace, so the first Core compile failed with two errors.

Correction: added the narrow import and rebuilt Core successfully before proceeding to Infrastructure.

Per-file atomicity was not aggregate atomicity

The initial storage sketch had atomic replacement for each JSON file, but a crash between files could still expose a mixed snapshot.

Correction: added generation numbers, per-file backups, and a manifest written last. The interrupted-save characterization now proves rollback to the committed generation.

The legacy loader was intentionally tolerant, but import must not be

JsonSettingsStore.LoadAsync historically recovers to defaults after unreadable JSON. Reusing that behavior during a destructive format migration could turn corruption into a successful empty import.

Correction: import reads the immutable backup through a fail-closed repository method and commits nothing if that backup is invalid.

Storage documentation and metadata assertions move together

The current-architecture snapshot is executable documentation: changing its phase and verification count requires updating the release metadata guard in the same change.

Correction: updated both and ran the focused metadata tests before the final full gate.

One final full run hit a timing-sensitive Phase 1 case

The follow-up-turn behavioral case briefly observed zero visible turns while the other 380 tests passed. No Phase 2 storage assertion failed.

Correction: isolated the exact case, passed it once and then 10/10 stress runs, and reran the complete Release suite successfully without masking or weakening the test.

What carries forward

Lessons for later phases

Stabilize one axis at a time

A disk migration is easier to prove when the in-memory model is pinned. Future domain-model changes can now target repository mappings instead of parsing legacy JSON everywhere.

A manifest is a small transaction log

Multiple atomic files need a shared commit decision. Generation matching makes partial writes detectable and recoverable without a database.

Import provenance is durable state

The manifest records the source release and import time, making one-time behavior observable and preventing a stale legacy file from regaining authority.

Deletion needs its own retention policy

Unreferenced conversation files are currently ignored. Removing them safely should be a separate, tested maintenance operation after the committed catalog has aged past a recovery window.

Phase boundary

What Phase 2 deliberately leaves stable

Application use cases still receive ISettingsStore, and the aggregate in-memory settings graph remains the compatibility surface. That is deliberate: the disk schema changed in this phase; later work can narrow use-case repositories without combining two migrations in one review.

Stable handoff

Durable ownership is now explicit, legacy import is reversible through its backup, and every loaded document must belong to one committed generation.
