Repairs

Four failures, three underlying defects

The failures were treated as evidence about ownership boundaries. Each correction was made at the narrowest layer that had lost or bypassed the relevant state.

Authentication status

Provider error context survives neutral event translation

Turn failure translation now retains provider error detail, recognizes 401/authentication failures, and emits an authentication-required event before completion. The completion snapshot therefore exposes an actionable sign-in state.

Queued dispatch — active and background

Named permission profiles no longer collide with legacy sandbox fields

The Codex request mapper now omits the legacy sandbox value whenever a named permission profile is present. This resolves the app-server rejection that blocked both active-thread and background-thread queue drains.

Reconnect

Feature loading goes through the runtime coordinator

Model loading no longer treats a cached harness session as proof that its provider transport is healthy. It asks the coordinator to ensure the session, allowing the established reconnect path to replace a failed app-server generation.

Background queue observation

The test follows asynchronous UI projection

The queue test now waits for the running state after durable removal is observed. Durable state is authoritative, while the UI continuation is eventually consistent on the captured synchronization context.

Repository policy

New guardrails make drift visible

Editor conventions

.editorconfig standardizes UTF-8, final newlines, whitespace, and indentation without introducing analyzer-driven source churn.

Build conventions

Directory.Build.props enables deterministic output and CI builds, with warnings promoted to errors in CI.

Central package versions

Directory.Packages.props owns all four external package versions. Existing versions were preserved exactly; dependency upgrades remain a deliberate future change.

Architecture boundaries

The tests assert the exact production project-reference graph, each project's namespace root, forbidden upward namespace imports, and that WPF/-windows targeting remains confined to SynthiaCode.App.

Dependency removal

SynthiaCode.Harnesses.Codex → SynthiaCode.Infrastructure was removed after source inspection, then verified by an isolated Rebuild with zero warnings and errors.

Candid record

Mistakes, corrections, and lessons

Queue diagnostics initially hid the useful failure

A helper timed out while waiting for the next message, obscuring the app-server's actual permission-policy error.

Lesson: asynchronous test timeouts should report the last application status and relevant durable state.

The background queue assertion assumed lock-step UI state

The test asserted IsRunning immediately after queue removal, although removal is persisted before the UI continuation runs.

Lesson: assert immediate durable invariants directly and await eventually consistent projections explicitly.

The first golden fixture did not compile

Its initial draft had one excess closing parenthesis and confused a raw Guid with the ConversationId value object.

Lesson: compile and run one new characterization class before expanding the surrounding phase.

The first namespace rule produced a false positive

A substring match interpreted SynthiaCode.Application as an import of SynthiaCode.App; its first compile also exposed nullable dictionary-key warnings.

Lesson: architecture rules are production code: compare namespace segments, keep failure output precise, and run them with warnings-as-errors.

The first central-package restore could not reach NuGet

The restricted process hit an SSL credential failure. The same unchanged restore succeeded once explicit network permission was granted.

Lesson: distinguish environment access failures from package-graph failures before changing dependency declarations.

Phase boundary

What Phase 0 deliberately did not do

No projects were split, no dependency versions were upgraded, and no provider-neutral model was redesigned. The new snapshots and dependency tests create a safe point from which the next structural phase can move code while proving behavior remains stable.

Changelog convention for later phases
